# 클로드 코드 개발 전 — 다듬을 부분 점검 목록

전제: 질문 인식은 HMOS로 구현·실증됨. 그 위에 루브릭→채점기준→부분점수→문항분석·논제생성을 클로드 코드로 개발.
설계·이론은 섰으나, 코드로 넘어가면 막히는 «덜 다듬어진 자리»가 남음.

## A. 봉인 규칙 — 가장 먼저 채울 것 (당신 몫, 최우선)
설계는 규칙의 «자리»만 비워둠. 코드가 돌려면 «내용»이 있어야 함. 없으면 코드가 조각을 지어냄(흉내).
- ① 파트 투영 — 네 파트를 문항 내용으로 매치하는 판정 기준
- ② 조각 역산 — 급소에서 «최소 핵심 수»를 셈하는 방법 ★핵심축, 이게 가장 무거움
- ③ 요소·색 판정 — 조각이 q·p·d·b·c·k 중 무엇인지 가르는 기준
- ④ k 무게 — 중심 조각의 배점·상한 규칙
- ⑤ 출구-조립 검산 — 지은 답이 급소와 일치하는지 통과/불통 기준
- ⑥ 파트별 조각 대조 — 학생 답에서 조각을 맞췄나 이분 판정
→ ②가 정해지면 ①③④⑤⑥이 따라옴.

## B. 설계에 있으나 덜 다듬어진 자리 (순서도)
- B-1. «일치?» 마름모 기준 — «solution ↔ 급소(질문 인식)» 일치로 못박기 (모범답안 기준이면 심판 함정)
- B-2. 두 장 순서도 연결 — 첫 장(생성)→둘째 장(사용), «생성 동시·사용 각자 시점»
- B-3. 네 파트가 순서도에 안 보임 — solution 모델 안에서 네 파트로 나뉘는 구조 표기

## C. 채점 실행 — 아직 안 정한 규칙
- 순서의 «상한» 구체값 — 앞 파트 무너지면 뒤에 얼마나 상한(0점? 감점? 채점불가?)
- 동점·경계 처리 — 학생 답이 애매할 때 이분 판정을 어느 쪽으로 (규칙으로, 재량 아님)
- 배점 반올림 — 배점÷조각수 안 나눠떨어질 때 (6점 4조각) 처리

## D. 문항분석·논제생성 — 방향만 있고 규칙 미정
- 문항분석(악문 감지) 기준 — 무엇을 «삐걱»으로 (조각 겹침? k 실종? 요소 결손?)
- 논제 생성 «급소 지정» 입력 — 급소를 어떻게 넣을지 (사용자? 성취기준?)
- 생성 문항 자가 검증 — 생성 문항을 입구로 다시 태워 급소 검산하는 루프

## E. 입력 통로 (OCR) — 구현 시 붙일 것
- 구조 정보 규약 — 밑줄=[밑줄:…], 수식=Mathpix 라우팅, «구조 살아있는 텍스트»
- 부실 감지 — OCR 결과 이상 시 «재료 불확실»로 멈추는 입구 감지

## F. 개발 운영 규율 (상시)
- manual mode 유지, 한 단계씩 승인. 자문자답 시 Esc.
- 파일 쓰기: 대상·백업·값노출 3가지 확인. 봉인 값은 개수·유무만.
- API 키 하드코딩 금지 — 환경변수. 매번 점검.
- 봉인 규칙(A)은 코드에 직접 안 넣고 «봉인 인터페이스로 호출».

## 우선순위
1. A(봉인 규칙), 특히 ②조각 역산 — 당신이 먼저 채울 것
2. B(순서도 다듬기) — 코드의 뼈대
3. C·D(채점·문항생성 미정 규칙) — 해당 단계 직전에
4. E(OCR 규약) — 입력 통로 붙일 때 / F(운영)는 상시
