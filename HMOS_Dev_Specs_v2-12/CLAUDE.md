# HMOS 채점기 기술 스펙
# Claude Code 개발용 — 2026 오종래

---

## 이 문서의 용도

Claude Code가 HMOS 채점기를 구현할 때 참조하는 **단일 진실 소스(single source of truth)**.
논문의 원리를 코드로 번역할 때 이 스펙을 기준으로 삼는다.

---

## 1. 시스템 아키텍처

```
[질문 Q 입력]
      │
      ▼
┌─────────────────────┐
│   PHASE A : HMOS    │  ← 네비게이션 (방향 결정)
│   루브릭 추출 엔진   │
└─────────────────────┘
      │ rubric + scoring_map
      ▼
┌─────────────────────┐
│   PHASE B : AI      │  ← 운전자 (채점 실행)
│   답안 대조 엔진     │
└─────────────────────┘
      │ axis_results + feedback
      ▼
┌─────────────────────┐
│   PHASE C : OUTPUT  │  ← 가시화 (결과 표시)
│   결과표 생성        │
└─────────────────────┘
      │
      ▼
[교사 최종 확정]
```

**핵심 원칙:**
- PHASE A가 없으면 블랙박스다
- PHASE C가 없으면 운전자만 아는 길이다
- 교사가 최종 확정하는 구조가 없으면 AI가 판단자가 된다

## 2. 데이터 스키마

### 2.1 입력 (Input)

```typescript
interface GraderInput {
  question: string;          // 원문 질문 전체
  student_answer: string;    // 학생 답안
  max_score: number;         // 총 배점
  subject?: string;          // 교과 (선택 — 없어도 동작해야 함)
}
```

### 2.2 PHASE A 출력 — 루브릭 패키지

```typescript
interface RubricPackage {
  // f(Q) 추출 결과
  M: string;                 // 재료: "무엇이 주어졌는가"
  C: string;                 // 조건: "어떤 제약이 부과됐는가"
  R: string;                 // 요구: "최종적으로 무엇을 보여야 하는가"
  K: string;                 // 급소: "이후 전체를 가르는 하나의 인식"
  T: string[];               // 함정: K를 놓쳤을 때 나타나는 오류 패턴들

  // 루브릭 4축
  rubric: RubricAxis[];

  // 채점 지도
  scoring_map: ScoringMap;
}

interface RubricAxis {
  axis_id: 1 | 2 | 3 | 4;
  axis_name: "개념" | "조건" | "논리" | "연산";
  source: "K" | "C" | "R" | "M";   // 어디서 도출됐는가
  criteria: string;                  // 판정 기준 (구체적 문장)
  score: number;                     // 배점
  pass_condition: string;            // ○ 판정 조건
  partial_condition?: string;        // △ 판정 조건 (있을 경우)
  fail_condition: string;            // ✗ 판정 조건
}

interface ScoringMap {
  primary_path: AnswerPath;          // 주경로 모범답안
  alt_paths: AnswerPath[];           // 대체경로 모범답안들
  error_types: ErrorType[];          // 예상 오류 유형
}

interface AnswerPath {
  path_id: string;                   // "primary" | "alt_1" | "alt_2" ...
  description: string;               // 이 경로의 풀이 방식 설명
  model_answer: string;              // 모범답안 전문
  rubric_results: {                  // 이 경로가 각 축을 통과하는지
    axis_id: number;
    result: "O" | "△" | "X";
    evidence: string;
  }[];
}

interface ErrorType {
  type_name: string;                 // 예: "누락형", "순열혼용형"
  trapped_axis: number;              // 어느 축에서 감지되는가
  pattern: string;                   // 오류 패턴 설명
  feedback: string;                  // 학생에게 돌려줄 피드백 문구
}
```

### 2.3 PHASE B 출력 — 채점 결과

```typescript
interface ScoringResult {
  student_id: string;
  matched_path: string;              // "primary" | "alt_1" | "error_누락형" ...

  axis_results: AxisResult[];

  total_score: number;
  max_score: number;

  error_type?: string;               // 오류 유형 (틀린 경우)
}

interface AxisResult {
  axis_id: number;
  axis_name: string;
  result: "O" | "△" | "X";
  score_earned: number;
  score_max: number;
  evidence: string;                  // 왜 이 판정인가 (근거 문장)
  feedback?: string;                 // 이 축에서 줄 피드백
}
```

### 2.4 PHASE C 출력 — 결과표

```typescript
interface ResultTable {
  // 학생용
  student_view: {
    total_score: string;             // "3 / 5점"
    axis_breakdown: {
      axis_name: string;
      result: string;                // "○ 1점" | "△ 1점" | "✗ 0점"
      what_i_did: string;            // 학생이 한 것
      what_was_needed: string;       // 필요했던 것
    }[];
    key_feedback: string;            // 핵심 피드백 한 줄
    next_step: string;               // 다음에 고칠 것
  };

  // 교사용
  teacher_view: {
    total_score: number;
    axis_detail: AxisResult[];
    error_type?: string;
    scoring_basis: string;           // 채점 근거 요약
  };

  // 학부모용
  parent_view: {
    summary: string;                 // 점수 아닌 내용으로
    understood: string[];            // 이해한 것들
    not_yet: string[];               // 아직 못 한 것들
  };
}
```

## 3. PHASE A — HMOS 시스템 프롬프트

Claude Code에서 PHASE A를 구현할 때 이 프롬프트를 사용한다.

```
SYSTEM:
당신은 HMOS 채점 엔진의 PHASE A (네비게이션)입니다.
주어진 서술형 질문에서 루브릭을 추출하는 것이 유일한 임무입니다.

반드시 지킬 원칙:
1. 루브릭은 생성하지 않습니다. 질문 안에 있는 것을 꺼냅니다.
2. 급소(K)는 반드시 하나입니다. 여러 개이면 질문 설계 오류입니다.
3. 모범답안을 먼저 만들지 않습니다. 루브릭 → 모범답안 검증 순서입니다.
4. 교과 이름에 의존하지 않습니다. 언어 구조(조사·어미)를 읽습니다.

추출 순서:
Step 1: 조사·어미를 기준으로 M(재료), C(조건), R(요구)를 추출합니다.
  - "~이/가 주어진" → M
  - "~할 때, ~인 경우, ~단" → C
  - "~하시오, ~을 구하여라, ~쓰고" → R

Step 2: M에서 K(급소)를 파악합니다.
  - 질문: "이 재료에서 하나의 인식이 이후 전체를 가르는가?"
  - 급소를 놓쳤을 때 나타나는 T(함정) 패턴들을 파악합니다.

Step 3: 루브릭 4축을 도출합니다.
  - K → 축1 (개념): 급소를 통과했는가
  - C → 축2 (조건): 제약을 빠짐없이 분류했는가
  - R → 축3 (논리): 요구를 구조로 구현했는가
  - M의 수치 → 축4 (연산): 계산이 정확한가

Step 4: 검증합니다.
  - 주경로 모범답안이 축1~4를 모두 통과하는가? (NO → 루브릭 수정)
  - 각 함정(T)이 어느 축에서 감지되는가? (미감지 → 해당 축 보완)
  - 대체경로가 루브릭을 통과하는가? (YES → alt경로 등재)

출력은 반드시 RubricPackage JSON 형식으로만 반환합니다.
다른 텍스트, 설명, 마크다운 없이 JSON만 출력합니다.
```

## 4. PHASE B — AI 채점 시스템 프롬프트

```
SYSTEM:
당신은 HMOS 채점 엔진의 PHASE B (운전자)입니다.
PHASE A가 제공한 루브릭을 기준으로 학생 답안을 대조하는 것이 임무입니다.

반드시 지킬 원칙:
1. 모범답안과 비교하지 않습니다. 루브릭에 대조합니다.
2. 총점을 먼저 내지 않습니다. 축별로 판정 후 합산합니다.
3. 판정마다 근거를 기록합니다. "왜 이 판정인가"가 없으면 무효입니다.
4. 경로가 다른 답안(alt경로)도 루브릭을 통과하면 만점입니다.
5. 답이 맞아도 논리 구조가 없으면 축3에서 감점합니다.

판정 기준:
- ○: 해당 축의 pass_condition을 충족
- △: partial_condition을 충족 (있는 경우)
- ✗: fail_condition에 해당

채점 순서:
1. 학생 답안이 주경로/alt경로/오류유형 중 어디에 해당하는지 판별
2. 축1 → 축2 → 축3 → 축4 순서로 각각 판정 + 근거 기록
3. 부분점수 확정
4. 오류 유형 분류 (틀린 경우)
5. 축별 피드백 생성

출력은 반드시 ScoringResult JSON 형식으로만 반환합니다.
```

## 5. PHASE C — 결과표 생성 규칙

```
결과표는 세 사람이 동시에 읽을 수 있어야 한다:

[학생용]
- 어디서 무엇을 놓쳤는가
- 다음에 무엇을 고쳐야 하는가
- 핵심 피드백 한 줄
- 점수가 아닌 행동 지침으로 끝날 것

[교사용]
- 왜 이 점수인가 (축별 근거)
- 오류 유형명 명시
- 학생에게 설명할 수 있는 언어로

[학부모용]
- 점수 대신 내용으로
- 이해한 것 / 아직 못 한 것
- 전문 용어 없이
```

## 6. 구현 시 반드시 지킬 것

### 6.1 절대 하지 말아야 할 것

```
❌ 모범답안과 유사도를 비교하는 채점
❌ 총점을 먼저 내고 이유를 붙이는 방식
❌ 판정 근거 없는 ○/✗ 출력
❌ 교사 대체 뉘앙스의 메시지
❌ AI가 최종 점수를 확정하는 구조
❌ 채점 기준을 교과 지식에서 가져오는 것
```

### 6.2 반드시 해야 할 것

```
✅ 루브릭 → 모범답안 순서 (모범답안이 먼저가 아님)
✅ 각 판정마다 evidence 필드 필수
✅ 다른 경로 답안도 루브릭 통과 시 만점
✅ 교사에게 결과를 인계하는 마지막 단계
✅ 세 사람(학생/교사/학부모)이 읽을 수 있는 결과표
✅ 학생 이력 누적 저장 (store)
```

### 6.3 경계 케이스

```
Q: 급소(K)가 여러 개로 보이면?
A: 질문 설계 오류다. K를 하나로 좁히거나 문제를 분리할 것.

Q: 대체경로(alt)인지 오류인지 판단이 어려우면?
A: 루브릭 4축을 통과하면 alt. 하나라도 안 통과하면 오류.

Q: 축4(연산)이 없는 문제 유형은?
A: R(요구)에 수치 도출이 없으면 축4를 0점으로 설정하거나 제외.

Q: 부분점수 △의 배점은?
A: 해당 축 배점의 50%를 기본값으로 한다. 문제별 조정 가능.
```

## 7. 실제 테스트 케이스

Claude Code 개발 중 검증에 사용할 기준 케이스.

### 7.1 문제

```
a, a, b, c, d, e가 적힌 6장의 카드를 일렬로 나열할 때,
양 끝에 모음이 오는 경우의 수를 구하고, 풀이 과정을 서술하시오.
```

### 7.2 정답 루브릭 (검증 기준)

```json
{
  "M": "a,a,b,c,d,e — 6개, 모음 a,a,e, a가 중복",
  "C": "양 끝에 모음 — 경우를 나눠야 함",
  "R": "경우의 수 + 풀이 과정 서술",
  "K": "a가 2개다, (a,a)가 존재한다 (B₂) — 조건 위에서 추적되는 실체",
  "T": ["누락형: a를 1개로 보고 2가지만 열거", "순열혼용형: 3P2 직접 적용", "독립사건형: 2×2=4 계산"],
  "rubric": [
    {"axis_id": 1, "axis_name": "개념", "criteria": "a가 2개임을 인식하고 풀이에 반영", "score": 1},
    {"axis_id": 2, "axis_name": "조건", "criteria": "양 끝 모음 조건(C₂)의 경우를 K(a 2개)를 반영해 빠짐없이 나눔", "score": 2},
    {"axis_id": 3, "axis_name": "논리", "criteria": "분리 계산 후 합산 구조가 드러남", "score": 1},
    {"axis_id": 4, "axis_name": "연산", "criteria": "경우별 계산과 합산이 정확", "score": 1}
  ]
}
```

> **2026-09-15 정정 (9/14 개정을 되돌림):** 9/14에 K를 "최심 요소 C₂"로 바꿨으나 오판이었다.
> 원전(제1강 7형식 표)은 급소를 일관되게 B 계열로 정의한다 — K = B₂ "a가 2개다, (a,a)가 존재한다".
> C₂(양 끝 모음)는 급소가 아니라 조건(축2)이고, T는 그 실체를 놓친 오류다.
> 축1(개념) criteria "a가 2개임을 인식"은 원래가 옳았으므로 그대로 둔다.
> 경로 표기 `θ°→B→C₁→[C₂]→C₁→B→θ*`의 대괄호 의미는 미결(BUILD_PLAN.md §5 이어갈 결정 1) — 손대지 않음.

### 7.3 학생 답안 채점표 — 폐기

> **2026-09-14 폐기:** 옛 K("a 2개") 기준으로 매긴 학생별 축 판정과 점수를 삭제했다.
> **2026-09-15 정정:** 폐기 사유였던 "K = C₂" 자체가 오판이었다. 확정 기준은 K = B₂("a가 2개다")이므로
> 삭제된 옛 채점표의 K 기준이 오히려 옳았다. 다만 **채점표 복원은 이 커밋에서 하지 않는다** —
> 3단계(PHASE B)에서 표5 점수 5·3·2·1·0 재현 검증과 함께 되살린다(BUILD_PLAN.md §2·§3).

## 10. 창의적 풀이 처리 — 모범답안에 없는 경로

### 10.1 원칙

```
모범답안에 없는 풀이 ≠ 오류

루브릭을 통과하면 만점이다.
경로가 달라도 논리가 같으면 같은 점수다.
채점기는 모범답안을 지키는 감시자가 아니라
질문의 의도에 도달했는가를 확인하는 자(尺)다.
```

### 10.5 alt경로 축적

```
교사가 ①을 선택하면:
→ ScoringMap.alt_paths에 추가
→ 다음 채점부터 자동으로 인정
→ 채점기가 쓸수록 alt경로가 쌓임
→ 쌓인 것이 이 채점기의 자산이 됨
```

## 11. 평가 솔루션의 철학 — 손전등

```
평가 솔루션은 손전등으로 구석구석을 비추는 것과 같다.
빛이 모든 곳에 닿게 하는 것이 목표다.

빛이 닿지 않으면:
- 모범답안에 없는 창의적 풀이가 오답이 된다
- 흐린 손글씨가 읽히지 않아 채점을 못 받는다
- 어느 축에서 틀렸는지 모르면 고칠 수 없다
- 학부모가 결과를 이해하지 못하면 신뢰가 없다

빛이 닿으면:
- 다른 경로의 창의적 풀이도 루브릭으로 인정된다
- 흐린 글씨도 맥락으로 읽힌다
- 축별 판정으로 어디서 무엇을 놓쳤는지 보인다
- 학생·교사·학부모 모두 같은 것을 본다

단, 손전등을 쥔 사람은 교사다.
AI는 빛을 만들고, 교사가 방향을 잡는다.
```

### 구현 체크리스트 — "빛이 모든 곳에 닿는가"

```
□ 창의적 풀이가 루브릭으로 인정되는가
□ 흐린 손글씨가 3패스 복원으로 읽히는가
□ 축별 판정 근거가 학생에게 보이는가
□ 교사가 이해할 수 있는 채점 근거가 있는가
□ 학부모가 점수 아닌 내용으로 읽을 수 있는가
□ 모르는 것은 모른다고 표시하고 교사에게 넘기는가
□ 교사가 최종 확정하는 구조가 있는가
```

*방향을 잡는 것은 사람이다.*
